# Web interface plugin

Distributed independently as `whab_plugin_web`. Bounded register and account metadata reads require WHAB 2.14 or newer. Its version and dependency compatibility range are defined in [pyproject.toml](pyproject.toml); its dated history belongs in [CHANGELOG.md](CHANGELOG.md). Material changes confined to this plugin update its version and changelog, without an app version or app changelog change.

`src/whab_plugin_web/` owns the bundled visual descriptor, view models, icons, Jinja templates and browser assets. Keep rendering and presentation tests alongside them in this folder. The host owns HTTPS routes and access guards through the public UI contract. Every request requires TLS; ordinary visual/private routes remain loopback-only, with only bearer-authorized remote protocol and verified bank-webhook routes exempt from local Host/origin checks.

Templates and static files must ship in the wheel. Use demo data for browser checks and preserve escaping and visual fallbacks.

## Live interface handover

WHAB 2.36 and Web 1.27 support the explicit visual lifecycle. The host captures a complete template/asset generation and serves its resources at `/budgets/{id}/ui/{generation}/static/`. Import maps use the same generation. Page and transaction fragments refuse a different generation, and budget autosaves retain the editor if a later totals fragment belongs to different code.

The browser registers opaque generation/edit flags with `/api/ui/views`; draft values stay local. Before handover it temporarily pauses shell input, flushes acknowledged edits, checks open dialogs/provider/import barriers and acknowledges readiness. Dirty or failed views defer the change while financial saving remains admitted. A clean committed view refreshes; an offline view keeps its old assets and drafts until it can safely refresh. Closed views expire from participation after 60 seconds. This coordination is not a browser security sandbox.

The host's local `/api/ui/status`, `/preview`, `/commit` and `/recover` controls prepare, review, schedule and reconcile the selection. A scheduled operation remains pending until its status confirms completion. Approved compatible code uses immutable worker environments; templates/helpers render inside the child from bounded public projections. Financial rules, HTTPS and access guards remain host-owned. Legacy visual descriptors with browser protocol zero retain restart-required behavior. The private device-local visual decision overrides initial `WHAB_UI` on reopen and preserves disabled interfaces and exact retained worker references; see [visual worker lifecycle](../../../../docs/plugin-workers.md#visual-interface-workers).

## UI acceptance criteria

For a material layout or interaction redesign, prepare a reviewable preview before implementation and retain the accepted layout/filtering feedback with the change. Use desktop and compact viewports, both appearances, and fictional data. Keep financial calculations in Python and preserve these interactions:

| Area | Acceptance check |
| --- | --- |
| Shell and view state | Same-budget/currency navigation keeps the sidebar, header, theme and shared dialogs mounted. In-place saves preserve the active field, newer drafts, expanded explanations, collapsed groups and scroll. Account switches preserve sidebar scroll. |
| Navigation and pending work | Exercise Budget, Transactions, Insights and Accounts, account switches, refreshes, rapid competing requests and Back/Forward. New views begin at the top; history restores view positions. Pending/failed saves, dialogs, imports and bank operations retain their existing navigation protections. A late response must never replace a newer view or draft. Cross-budget/currency changes retain full-navigation behavior. |
| Keyboard and accessibility | Reach dialogs, inputs, disclosures and filters with the keyboard; verify focus, accessible names and save/error feedback. Account picker arrows/typeahead move, Space toggles, Enter applies and Escape cancels. Search retains selected accounts; Select all covers every available account, Select none clears the draft, and Apply requires a selection. |
| Ledger behavior | Check single/multiple account selections, inclusive/open date ranges, search and review filters, pagination, memo/category edits, single/bulk review, pending rows, suggestion acceptance/dismissal and receipt availability. Filters and addresses must identify the same budget, accounts, period and currency after navigation. |
| Failure and fallback | Check failed saves/retry identity, missing images, unavailable capabilities and an older compatible remote host. Keep usable text and keyboard controls; do not invent totals or silently write to another ledger. |

For rendering or navigation performance changes, compare the same fictional workload before and after from `whab/app/`:

```sh
.venv/bin/python scripts/benchmark_register.py --accounts 31 --transactions 31000 --requests 5 --all-accounts
```

Use `--page accounts` or `--page budget` for the affected view, `--summary` for review summaries, and `--profile-memory` when allocation changes matter. Record the workload, route/filters, environment, response size and measured rendering result. These measurements exclude browser layout/network time; also exercise a disposable Sandbox runtime with comparable fictional history in the browser, retaining any seed fixture with the change. Observe initial display, interaction response, loading/error feedback, scrolling and network/console failures while editing and navigating. Report a regression or improvement against that baseline rather than inventing a numerical latency target. See the [development runbook](../../../../docs/development.md) for disposable runtime setup and running-version verification.

## Register rendering and navigation

Model category predictions display a small forest icon beside the **ML suggested** badge in the transaction register. The same icon identifies Random forest categorization in the installed-plugin list. Suggested categories remain provisional until manual review.

Compatible model settings expose **Preview low-score guesses**, an explicit action that includes uncertain guesses for review without changing the automatic score cutoff. The register shows the score and **Low score** on these predictions. This action requires WHAB 2.20 or newer and a compatible categorization plugin on the budget host.

The descriptor opts into `transaction_page_size=100` and `lightweight_accounts=True`. The host supplies bounded rows and complete-selection counts, while this plugin builds filter controls, page links and labels. Older storage plugins retain public-read fallbacks. Account and merchant images begin loading near visible fallback marks, with at most two requests at once; closed account pickers wait until opened. Errors, detached rows and a ten-second load deadline release image slots. Explicit account-logo previews remain immediate.

Large transaction selections render at most 100 editable rows at a time. Payee and memo search and the review filter apply across the entire selected account/date range before pagination. Previous/Next preserves those filters and pending edits finish before the view changes. The `q` and `tx_page` query parameters retain search and page state in bookmarks; search also works as a normal GET form without JavaScript. Export still contains the complete selected currency. All web module dependencies use the plugin version to load matching scripts after an update. For isolated rendering measurements with fictional data, run `.venv/bin/python scripts/benchmark_register.py --all-accounts` from the application directory; the script also accepts `--page accounts` and `--page budget`. It measures server rendering and markup size, excluding browser layout and network time.

Under All with an empty search, successful review changes request only a small server-rendered summary, keeping the current rows, editors and listeners in place. Search and review-filtered views still refresh their complete visible page. Summary responses validate the addressed budget, currency, account/date filters and requested page before changing the count; canceled or superseded responses cannot replace a newer view. Use `--summary` in the benchmark to compare response size. `--profile-memory` separately measures Python request allocation peaks; it excludes SQLite/native memory and the browser.

The two account dialogs initially contain only the selected currency option. Opening either dialog fills its choices from one compact server-rendered currency catalogue before showing the controls; loaded account settings apply their currency after hydration. Currency history locks, reset defaults and server-defined minor units remain unchanged. This reduces hidden DOM elements without another request or module.

Ordinary register navigation asks to omit the sidebar account-list template that it leaves in place. Explicit refreshes still request the updated account list, and clients without this optional header receive the complete fragment. Fragment responses remain uncached, and the host's `Vary` header covers both fragment selectors.

When the host advertises atomic bulk review, pure review changes share requests of at most 100 transactions. Existing row writers retain save/error states and ordering for memo and category drafts. Failed batch tickets keep their original request identity and are confirmed before later edits; a submitted batch never silently switches to individual writes. Providers without this capability retain the existing four-worker path. Pending rows remain excluded from the bulk controls, and navigation waits for outstanding saves.

After successful partial navigation from the budget planner to an account register, the detached budget editor releases its form records and listeners. Navigation still waits for saved edits; a new budget draft cancels a pending account request so its response cannot replace that draft.

Budget, Transactions, Insights and Accounts navigation within one budget and currency replaces only validated server-rendered main content. The sidebar, header, theme and shared dialogs stay mounted, and the previous content remains visible while loading. Budget/register controllers and per-view controls are initialized again on entry; account and category choices refresh without replacing dialog drafts. New navigations start at the top, and Back/Forward restores recorded view positions. Open dialogs, active provider operations and failed or newer edits block replacement. Cross-budget/currency links and incompatible asset versions use normal document navigation. Generic pages and register refreshes share one cancellation sequence, so an older response cannot replace a newer view.

On hosts advertising bounded receipt indexes, register loads request markers only for the current page's at most 100 transactions. Older hosts retain the full-index request, and empty pages make no marker request. Receipt buttons stay disabled until the index succeeds; errors do not trigger another request path. Image viewing, upload, deletion and portable persistence use the existing receipt operations.

The sidebar footer shows a green status dot and the running WHAB application's version, using the host version supplied with the page. An icon-only Settings button sits at the far right of the same row, with a Settings tooltip and accessible name. Compact screens retain the Settings button while hiding the status dot and version.

## Addresses

Browser views use `/budgets/<budget-slug>/<page>/<month>/<currency>`; account registers use `/budgets/<budget-slug>/<account-slug>/transactions/<month>/<currency>`. Names become lowercase, hyphenated aliases with accented Latin normalization and Cyrillic transliteration. Duplicate names get numeric suffixes, and old aliases remain valid after renames through a device-local registry. Permanent IDs still scope API calls/assets; old UUID, `home` and `?account=<id>` links continue to work. The single sample budget remains `demo`. Pages are `budget`, `transactions`, `insights` and `accounts`. `current-month` follows the calendar on each load; an explicit `2026-10` stays fixed. Page and currency links preserve the month token; month arrows select an explicit month. Category selections may use query parameters. The root opens the initial demo or selected saved budget; an explicit `--budget` or `WHAB_BUDGET` launch starts only that selected runtime and opens its readable address. `home` remains available on ordinary local launches, and demo uses the startup runtime's sample data. Old root query-style view addresses are not supported. See [budget addresses](../../../../docs/usage.md#budget-addresses).

The host scopes page context, API requests, plugin assets and downloads by the address's budget so another tab's selected-budget cookie cannot redirect an operation. Browser scripts retain uppercase ISO currencies in API payloads. These routing inputs and targeted downloads require WHAB 2.6 or newer.

## Budget planner

The budget workspace offers Light and Dark appearances with the compass logo's red and yellow accents. Compact month cards align over three months of **Income**, **Carried in**, **Assigned for next month**, **Assigned this month** and **Available to assign**, with one amount per row and month. Carried in is explicitly labeled as previously unassigned money, money set aside for this month, and overall category carryover. Its expandable breakdown uses core's existing component amounts; category-mode balances remain exclusively in the category Carryover columns. Assigned for next month is an independent transfer out of this month's assignable pool and into next month's carry-in; it can be below next month's category assignments. Plain values and Summary labels distinguish read-only totals from outlined editable amounts. Detailed Carryover, Assigned, Activity and Available headings appear within Spending categories, with sticky labels, parent summaries and editable child assignments. Selected navigation items and category labels use a flat yellow fill without a separate accent edge; navigation corners are square. Settings remains at the bottom left.

Every read-only amount in the overview has a native **Where it comes from** disclosure for its own month. Income explains received money and links to that month's transactions; historical income before the budget starts is identified as history. Assigned this month points to the matching Assigned total at the bottom of the spending table. **Show matching total** focuses that total and highlights both matching values without repeating every category. Available to assign shows Income plus Carried in minus Assigned for next month minus Assigned this month, using core's actual component values and signed result. Carried in retains its component breakdown. Editable next-month funding stays an input; a valid read-only fallback explains the saved set-aside. Unavailable amounts never receive a fabricated explanation. Disclosures work with the keyboard and retain the selected currency's precision.

Budget assignments and rollover choices save in place, with local saving, saved and error feedback. Rollover feedback has its own reserved line beneath the choices, inside the month card. Edits are serialized without locking unrelated fields. After a validated save, a small server-rendered budget fragment updates only changed DOM values; the active field, newer drafts, scroll position, expanded explanations and collapsed groups stay in place. Python remains the authority for all amounts. The fragment is requested at the same budget address with `X-WHAB-Budget-Fragment: 1` and uses the same HTTPS, budget scoping and no-store protections as the full page. It contains the budget planner without the navigation shell or dialogs. The bottom of the table retains Add category without repeated currency or planning notes.

The descriptor requests `budget_months=3` and requires WHAB 2.9 or newer. The host supplies selected-currency public projections in `data['periods']`; the plugin formats core's `summary.carriedIn`, `carriedInUnassigned`, `carriedInSetAside`, `balanceCarryover`, `assignedNextMonth`, `assigned` and `readyToAssign`. Core advertises `monthlyFundingFlow: true`; the UI requires that exact capability together with `nextMonthFundingEditable: true` before editing independent next-month set-asides. Until an older remote server is upgraded, Carried in, Assigned for next month and Available to assign display dashes, and next-month editing is unavailable. Missing or invalid totals also display dashes. No next-month editor appears before the budget starts or at `2200-12`. Saving sends the displayed source month, currency and amount to `PUT /api/budget/funding/next-month`. If core's conservative `fundingCapacity` is below the monthly pool total, a note inside **Where it comes from** explains that spending or account reserves limit new assignments. Budget rules remain in core.

Each month's **Carryover** radio group offers **By category** and **Overall balance**, followed by **Into <next month>**. The first carries category surpluses and deficits individually; the second resets incoming category balances and exposes their signed net in **Carried in**, already included in general cash. The control saves the displayed source month and currency to `PUT /api/budget/settings/rollover`, and uses the per-currency `rolloverMode` and literal `rolloverModeEditable: true` capability. Older servers, pre-budget months and the final supported month remain read-only. Editing an earlier rule recalculates subsequent months and saves even if it creates a funding shortfall. Each affected month shows a red **Funding shortfall** note, including when its monthly pool is positive but spending or account reserves make funding capacity negative. Its Available to assign disclosure shows the exact signed capacity when it is below the pool; category and pool balances retain their own signs. A receiving month whose `incomingRolloverMode` is `category` shows a read-only **Carryover** column before Assigned, including positive, zero and negative amounts and calculated group and monthly totals. The previous month's rule controls this column even when that month is outside the displayed window. The first budget month and months receiving an overall balance use the three-column layout. Available amount tooltips also show carried-over, assigned and activity values.

## Accounts and transactions

The compact transaction table has independent multi-select checkboxes, Date, Receipt, Payee, Category, Memo, signed Amount, Currency and a small **R** reviewed toggle. When multiple accounts are selected, including All accounts with more than one available account, Account appears immediately after Date with each transaction’s account name. Single-account registers omit that column. Pending transactions cannot be reviewed. Category, memo and review edits save in place, with serialized writes and retry feedback. Sidebar account changes fetch only the main register, preserve sidebar scroll and support Back/Forward. Transaction pages use a scoped core projection that skips envelope and trend calculations; SQLite reads only the addressed accounts/date range/currency rows in one snapshot. Category choices are rendered once and populated on focus or pointer interaction, retaining native keyboard behavior. Financial page HTML is never cached for reuse. Outstanding edits finish before navigation. The account picker supports multiple choices and uses existing optional bank logos, with local decorative images and generic fallbacks. Search filters account names without removing selected accounts from the draft. Select all chooses every available account, including accounts outside the search results; Select none clears the draft so a new subset can be chosen. A selected count makes multiple selection explicit, and Apply remains disabled until at least one account is selected. Apply batches selections into one register update; arrows and typeahead move, Space toggles, Enter applies, and Escape cancels a draft. The period picker offers This month, Previous month and inclusive custom start/end dates; either bound can remain empty. Legacy All dates links appear as Custom dates with open bounds. The top R filter cycles Needs review, Reviewed and All immediately and keeps its state in the URL. Legacy month/account/all-dates bookmarks remain valid.

Receipt images are optional storage-owned attachments, available with SQLite: JPEG, PNG or WebP up to 5 MiB and 25 megapixels each. Save, open or remove an image from the Receipt column. They stay with the budget across restart and portable export; a storage plugin without attachment support leaves the control unavailable. Receipts are private budget data and never sent to a bank or artwork provider.

Transactions display merchant artwork supplied by the enabled Plaid plugin through a local image route. The payee name and editable memo remain visible; artwork loads independently and falls back to the merchant's initial on failure. Transactions without supplied artwork keep their text-only presentation.

Accounts and the sidebar separate **On-budget** everyday accounts from **Off-budget** assets and debts. On-budget checking, savings and credit accounts participate in budget income and spending. Off-budget investments, retirement accounts, property, loans and deposits (including CDs) contribute to net worth while their transactions remain available for review. Assets, liabilities and net worth use current known balances in the selected currency; stale and unavailable snapshots are excluded. Currencies are never combined. The sidebar shows each account’s recorded balance rounded to the nearest whole currency unit, with half units rounded away from zero and debts shown as negative amounts. It omits decimal places and approximation markers; hover or screen-reader text explains whether a balance is current, last known or estimated from YNAB’s exported transactions. YNAB estimates retain their exported sign, even after account classification, and remain excluded from funding and net-worth totals until a verified balance is available. Accounts with no usable balance continue to show `—`.

Choose an individual sidebar account to open its transactions across all dates. The account picker and heading identify the register; use the period picker for This month, Previous month or custom inclusive date bounds. The main **Accounts** navigation opens account management. Account and date filters remain in the address, and switching currency clears the account selection.

**Add manual account** offers budget scope, account type and relevant account details, such as brokerage, Roth IRA, 401(k), home, mortgage or CD. Enter liabilities as the positive amount owed. **Account settings** in an individual register changes the account name, scope, type and detail. Scope applies to every transaction in that account and updates budget totals accordingly. Currency can change only before any transaction history exists, including deleted history. Names survive bank refreshes. When Bank logos is active, Account logo accepts a bare domain or full URL, identifies the plugin and its Settings, and explains that only the public domain goes to Icon Horse (`icon.horse`). **Retrieve logo** sits beside the Bank website field and previews artwork immediately without saving account metadata. Pressing Enter in that field retrieves the logo instead of saving the account. Missing, invalid or unavailable artwork produces a neutral status and does not block Save. Retrieval is optional; a saved website can resolve when its sidebar image loads. Downloaded logos stay cached indefinitely across restarts.

## Settings and appearance

Settings contains **Budgets**, **Plugins**, and **About this prototype**. The Budgets dialog has three titled sections. **Open budget** lists every budget in the host catalog alongside the single **Demo budget** destination, with a radio selection, one **Current budget** marker, and a separate **Download** button on each row. Downloading preserves the selected budget; a demo download contains only fictional data and opens as a fresh budget. Enter a password if needed, then choose the red **Open selected budget** button to switch. **Create new budget** contains the name field and **Create budget** action. **Add budget** contains a WHAB file chooser, an optional password and **Add as a separate budget**. Its **Add budget** action adds the file to the catalog and opens it. All three actions leave Settings only after success; failures keep the dialog and entered information. Switching budgets preserves the page, month and currency while clearing the previous category selection. Linked portable file copies and encrypted remote-credential exports remain under **Saved copies and export options**. The core owns budget creation, persistence, isolation and downloads; this plugin owns presentation and navigation. The same controls work on desktop and mobile.

**Settings → Plugins → Installed → a storage plugin → Settings** shows **Primary**, **Synced copy**, and **Not used** for the current budget. These roles are independent of optional plugin enablement. Exactly one storage plugin is primary; it cannot be made unused until another copy is promoted. Radios reflect confirmed host status, including while a change is pending or fails. Choosing **Synced copy** prepares an empty native destination and requires explicit attachment confirmation. Choosing **Primary** on an unused plugin first reviews attachment, then opens a separate promotion review after the attached copy is confirmed. Cancelling that second review leaves the synced copy in place. Existing synced copies go directly to promotion review; multiple copies require choosing the particular copy under **Saved copies and status**. Choosing **Not used** reviews stopping synchronization for all copies of that plugin while retaining their saved data. Inactive installed storage plugins still expose these host-managed controls; Demo stays read-only.

The optional copy API requires WHAB 2.30 or newer and a compatible native storage plugin. Unsupported hosts/backends leave roles read-only. **Saved copies and status** expands financial and plugin-state revisions, attributable failures, retry, disable and individual promotion controls. A successful primary save remains successful when copying fails. Accepted and running changes stay pending until host status confirms the new authority. The host catches up and validates the copy, retains the previous primary, and owns financial and persistence decisions; see [storage copies](../../../../docs/storage-replicas.md).

The dialog flushes outstanding edits through the existing save guard before changes and never reloads the page. Closing stops browser polling while accepted host work continues; reopening reads its current status. Unknown mutation responses trigger status reconciliation without an automatic repeat. If no outcome can be confirmed, **Review refreshed status** explicitly returns to the observed status before another reviewed action. Unsupported hosts/backends show read-only guidance. Demo offers a link to the personal budget. Recovery and changed-source attachments pause affected controls, and no private namespace contents, filesystem paths or credentials appear in the dialog.

Open **Settings → Plugins → Installed** to select plugins. The category filter starts with **All categories**, with alphabetical category sections and plugin names. Example plugins are hidden, and valid existing example selections survive saving other choices. Required storage and interface plugins stay selected. Choose **Review live selection**, then **Apply reviewed change**, to request a supported live optional change. The host checks capability support and unfinished work; unsupported selections remain available through **Save selection for restart**. Saving for restart preserves the running plugins until restart. A queued or running request is shown as pending until host status confirms completion. Lost replies trigger status inspection without repeating the request.

The **Visual interface** section in the Plugins dialog shows the host-confirmed plugin ID, resource generation and runtime health. Enter an exact installed visual plugin ID (for example `web`), or choose **Headless**, then **Preview interface change**. Review the target and explicitly choose **Apply reviewed change**. API interface plugins belong in the separate optional selection. Preview does not import inactive code merely to populate a choice list; it validates only the explicitly requested target. This control uses installed code, while approved-wheel upgrades remain an explicit host API operation.

Before applying a visual change, the dialog flushes saved edits and checks existing continuation guards. It closes the Settings and Plugins dialogs so this browser can acknowledge the host’s existing unsaved-view barrier; any other open dialog blocks the request. Other browsers must also acknowledge. Accepted work continues if the dialog closes. Reopening or refreshing reads host status, and an unconfirmed reply requires a refreshed status review before another submission. Headless removes browser pages; use the local host or recovery controls to restore a visual interface. Demo shows read-only guidance. Resource URLs retain the selected generation throughout the change. If the host retains a failed resource cleanup, **Retry cleanup** requests one bounded reap attempt, then refreshes the counts. It does not restart a child, repeat a plugin change or clear financial recovery.

Every visible installed-plugin row has a **Settings** page; hidden teaching examples have no ordinary Settings row or Settings page. Each installed row aligns the plugin name, package and version, saved enabled state, and **Settings** action in that order. Each Settings page includes its category, version, saved selection and running state. Running plugins can expose generic settings information and actions through the public SDK; inactive plugins explain supported live selection or restart without running their settings hooks. Settings values and action feedback render as text. The bank-logo plugin uses this page to show its indefinite cache policy, cached count and public artwork source; **Flush cache** clears downloaded artwork and failed requests while preserving saved bank websites and account settings. Images download again when next requested.

Enabled file importers render their upload form in **Settings**, from every page including Demo. **Import from YNAB ZIP file → Settings** explains that **Create budget and import** creates and opens a separate budget after preview; the Accounts management page contains no import panel. Dropdowns share inset, centered chevrons while retaining native keyboard and high-contrast behavior.

**Download** keeps credentials on the device. The additional export form can explicitly include a password-encrypted remote access credential. Only that credential is encrypted; the rest of the container remains readable plugin data, and bank-provider tokens are never included. Upload and saved-budget switching accept an optional password without placing it in URLs or browser storage.

Choose **Settings → Plugins → Installed → WHAB web → Settings → Appearance**, then **Light** or **Dark**. The change applies immediately across the web interface. The preference is remembered in this browser for the current origin (hostname and port), independently of financial data and portable budget settings. With no saved choice, the initial appearance follows the browser's system preference. When browser storage is unavailable, switching still works for the current page. The appearance script restores a saved choice before the stylesheet loads; web assets use the web plugin's version so plugin-only updates refresh their styling.
